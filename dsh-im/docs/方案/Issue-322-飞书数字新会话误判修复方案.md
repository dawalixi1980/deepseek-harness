# Issue 322 飞书数字新会话误判修复方案

采用局部修复：保留数字回复的串行消息队列，只在主菜单数字 `2` 执行新会话操作时跳过 `#queues` 占用检查，继续检查待回答和待审批状态。修改一个生产源码文件，并在现有测试文件中补充回归用例。

日期：2026-10-07。状态：已实施，自动化检查及本机飞书验收通过。源码基线：`fe2395b`，包版本 `4.36.1`。需求来源：[Issue 322](https://github.com/xmanrui/dsh-im/issues/322)。

## 已确认的问题

本机飞书机器人“今天是牢梁”在 2026-10-07 01:09—01:10（Asia/Taipei）通过真实客户端复现：发送 `/m` 后回复 `2`，收到“当前任务仍在运行”；点击同一张菜单的“停止”，收到“当前聊天没有正在运行的任务”。测试前后原会话绑定和会话日志一致，最后一个任务轮次已经完成。

该运行实例的 `/version` 返回 `4.35.1`；磁盘源码为 `4.36.1`。真实复现对应前者，源码分析和本地模拟复现对应后者。本机证据保存在 `output/issue-322-live-20261007/` 的 `results.json` 和 `feishu-reproduction.png`，不随代码提交上传。

数字消息先由 `#enqueueMessage()` 登记到 `#queues`，然后依次进入 `#handle()`、`#handleMenuPick()` 和 `#handleCardAction('new')`。最后一个方法检查 `#queues.has(key)`，把自身正在执行的数字消息误判为运行中的任务。

这里的 `#queues` 保存整条消息处理链，可能还包含后续排队消息，不是 AI 任务的专用运行标志。

## 最小修改

文件：`src/channels/feishu/bridge.mjs`。

1. 给私有方法 `#handleCardAction()` 增加内部参数 `fromMessageQueue = false`。
2. 在 `#handleMenuPick()` 的主菜单分支调用该方法时，仅对 `action === 'new'` 传入 `fromMessageQueue: true`。
3. 只调整 `#handleCardAction('new')` 普通分支的队列判断：

```js
if ((!fromMessageQueue && this.#queues.has(key))
  || this.#hasPendingInteraction(key)) {
  // 沿用现有忙碌提示并返回。
}
```

该参数由内部调用点设置，不从飞书消息或卡片回调载荷读取。保留现有清除绑定、成功回执和菜单刷新逻辑；不复制一份新会话实现。参数旁添加简短注释，说明它依赖同一聊天消息串行执行的前提。

`/new` 的独立分支、真实卡片按钮及 `#handleNewSessionMenu()` 的检查保持原样。其他菜单数字操作不使用这一例外。

## 为什么可以跳过检查

当前数字菜单分支在普通消息队列内部执行。`#enqueueMessage()` 等前一条消息完整结束后才调用当前消息的 `#handle()`，因此轮到数字 `2` 时，同一队列前面的任务已经退出。后面的消息也要等数字 `2` 完整结束后才能开始。

此时 `#queues.has(key)` 只能说明当前处理链尚未完成，不能据此拒绝当前新会话操作。跳过这一检查既不删除队列记录，也不提前释放队列；待回答和待审批的检查仍然保留。

沿用现有调度后，用户行为如下：

| 场景 | 修复后的行为 |
| --- | --- |
| 空闲时主菜单回复 `2` | 清除当前绑定，回复新会话成功 |
| 任务运行时回复 `2` | 排在当前任务之后，任务结束后再开启新会话 |
| `2` 后面还有普通消息 | 先完成新会话操作，后续消息按现有逻辑进入新会话 |
| 任务运行时发送 `/new` 或点击新会话按钮 | 沿用现有立即提示忙的行为 |
| 数字被问答或审批处理器接收 | 沿用原交互优先级，不转成新会话命令 |
| 没有主菜单、菜单已过期，或正在选择会话列表中的第 2 项 | 沿用对应的原处理路径 |

数字 `2` 的排队行为与 `/new` 的立即反馈并不完全相同。本次接受这一已有调度差异，以最小改动修复误判；不把所有数字回复提前到快速命令入口。

## 范围边界

本次不新增状态机、任务注册表、配置项、持久化字段或跨渠道抽象，也不修改共享 Harness 控制权判断。

Issue 中“停止失败后可能残留问答或审批”的情况另行处理。真实复现无需这种残留就能发生，不能据此把“停止返回 false 时无条件清理交互”并入本次补丁。

仅在 `#handleMenuPick()` 内再套 `await #queueCardAction()` 无法消除外层消息的队列占用；直接移除所有新会话入口的 `#queues` 检查则会影响真实运行任务的保护。两者都不采用。
