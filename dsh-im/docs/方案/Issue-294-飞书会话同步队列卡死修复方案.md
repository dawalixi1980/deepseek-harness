# Issue 294 飞书会话同步队列卡死修复方案

日期：2026-10-03。问题：[Issue 294](https://github.com/xmanrui/dsh-im/issues/294)。实施基线：`main` 的 `c6c5177`，包版本 `4.34.1`。分支：`codex/fix-feishu-session-sync-timeout`。方案已实施，自动检查与本机受控故障验收通过。

建议将超时保护加在实际飞书 SDK 调用的等待边界，复用飞书文件投递已有的限时等待封装。卡片请求挂起时，让它转为现有的失败处理：停止本轮卡片更新、允许文字兜底、释放会话队列，随后继续处理新轮次。生产改动集中在 3 个模块，沿用现有串行队列、卡片状态和恢复机制。

## 已确认的问题

`FeishuHarnessBridge.#queueEventTask()` 能处理任务拒绝，但不能处理任务一直处于 pending。封存先等待 `card.renderChain`，再更新最终卡片；这两个阶段的 SDK 请求只要一直不返回，封存就不会结束。下一轮事件、历史检查和补偿任务都会排在它后面。

Host 的同步协调器还会等待镜像结果，收到失败后才发送最终文字。因此持续 pending 会同时阻止文字兜底，并延迟同一 Session 的其他同步目标。重启可以创建新的内存队列，并沿用已有镜像快照收尾。

Runtime 已设置默认 15 秒 HTTP 超时，但没有对整个 SDK 调用的等待设置硬期限。现有复现通过注入不返回的 SDK Promise 验证队列缺陷；线上首次挂起的具体调用，以及真实网络为何没有触发 HTTP 超时，仍需日志和真实网络实验确认。

## 最小改动

| 模块 | 修改内容 | 复用的机制 |
| --- | --- | --- |
| `src/channels/feishu/feishu-channel.mjs` | 将现有 `waitForFileOperation()` 的等待逻辑小范围复用为内部导出的 `waitForFeishuOperation()`，允许调用方指定超时操作名称。文件投递继续使用原来的错误映射和 120 秒限制。 | 现有定时器、AbortController、只落定一次的保护，以及定时器和监听器清理。 |
| `src/channels/feishu/bridge.mjs` | 保护 `#sendCard()` 内的 SDK 创建、更新、回复调用，以及 `#patchStepCard()` 内的更新调用。接收 Runtime 透传的 `requestTimeoutMs`，直接实例化 Bridge 时默认 15 秒。 | `card.broken`、封存返回 `null`、`mirror.result.ok = false`，以及原有队列和恢复路径。 |
| `src/channels/feishu/feishu-runtime.mjs` | 透传已有 `requestTimeoutMs`；对 `sendProactiveText()` 内的 SDK 创建调用使用同一封装，覆盖 Web 输入回显及最终文字兜底。合并调用方取消信号与 Runtime 停止信号。 | 已有请求超时参数、Runtime 生命周期和主动文字投递入口。 |

超时值直接沿用现有 `requestTimeoutMs`，默认 15 秒，不增加用户设置。现有 HTTP 超时继续保留，新增保护负责保证调用方等待能够结束，即使 SDK 或替身忽略取消信号也有效。

保护应放在每次实际 SDK 调用上，形式如下。闭包只发请求，状态更新保留在等待成功之后：

```js
const response = await waitForFeishuOperation(
  () => this.#client.im.v1.message.patch(payload),
  { signal: this.#signal, timeoutMs: this.#requestTimeoutMs },
);
```

## 超时后的处理

运行中创建或更新超时，进入 `#renderStepCardNow()` 现有 catch，设置 `card.broken` 并记录警告。后续过程更新沿用该标记退出，封存返回失败，Host 通过原有路径补发最终文字。

最终封存超时，进入 `#finishStepCard()` 现有失败处理；是否能确认答案已经可见，继续由已有回执和答案版本检查决定。不能确认时返回失败，文字同步继续兜底。普通 IM 轮沿用原来的富文本和纯文本降级路径。

超时转为拒绝后，原有事件队列继续执行后续任务。`#checkMirror()` 可以继续使用相同队列和 30 秒检查定时器；Host 协调器也继续使用现有镜像回执和文字投递流程。飞书文字发送自身超时时，向原有上层失败处理返回错误，使协调器能够结束本次投递并处理后续事件。

最后一次成功的镜像快照继续保留，成功确认封存后才清理，重启恢复沿用 `#sealOrphanMirrors()`。日志在已有 warn 路径中标明超时操作和已知的 Session、turn 信息。首版用户回复沿用现有最终答案文案；额外的过程卡失败提示不作为解除阻塞的前置条件。

## 避免迟到结果恢复旧任务

直接给整个 `#queueEventTask()` 套 `Promise.race()`，会让旧任务在后台继续运行；队列已放行新任务时，旧任务仍可能更新卡片或写状态，需要额外解决并发和任务隔离。

本方案将限时等待放在 SDK Promise 边界。超时后 Bridge 的 await 拒绝，控制流进入现有 catch；SDK 迟到的成功或失败由等待封装接住，不再恢复旧的 Bridge 控制流。验证时需要检查它不会补写镜像、重复发送答案或继续请求下一张卡。

这只能保证本地控制流退出，不能撤回已经发到飞书的请求。超时代表未能确认结果，不证明平台没有接受请求。沿用现有文字兜底策略，可能出现迟到卡片与兜底文字同时可见；不因超时自动重发同一次卡片创建，也不增加新的重试循环。

## 回归测试和验收

复用现有 `session-sync.test.mjs` 的 Bridge、协调器、镜像存储和事件 fixture，替换外部 SDK 请求为持续 pending；使用现有 Node 模拟定时器推进时间。超时测试自身也设置有限期限，避免回归时测试进程永久等待。

| 场景 | 验收结果 |
| --- | --- |
| 首次卡片创建持续 pending | 到期返回失败；完成轮次的最终文字仍可兜底；同一实例的下一轮正常生成卡片。 |
| 运行中卡片更新持续 pending | 卡片变为 broken；封存能够结束；下一轮恢复。 |
| 最终封存更新持续 pending | 返回已有失败结果；最终文字兜底能够执行；其他同步目标收到最终答案。 |
| Web 输入回显或最终文字发送持续 pending | 飞书投递到期返回错误；协调器能处理后续轮次，其他目标不被永久拖住。 |
| 超时后旧 SDK 请求才成功或失败 | 本地镜像不被旧控制流补写；不重复发送答案，不继续发起旧轮次的请求；没有未处理的拒绝。 |
| Runtime 停止或调用方取消 | 当前等待退出；已取消操作不再启动 SDK 请求；清理定时器和监听器。 |
| 正常消息、真实长工具和既有失败恢复 | 继续保持原有答案去重、长工具运行状态、分片和快照恢复行为。 |

文件投递现有测试必须继续通过，确认复用等待封装没有改变其超时、取消和错误语义。实现后运行飞书 session-sync、Bridge、Runtime、Channel 及 Host 协调器相关测试，再执行 `npm run check` 和 `git diff --check`。

最后用真实 SDK 对受控的本地 HTTP 服务注入无响应，检查现有 HTTP 超时与新增 SDK 等待期限的协作。真实飞书验收检查一次故障后的下一轮可以继续生成卡片；将模拟验证与真实网络结果分别记录。

## 已完成的原型验证

当前代码注入持续 pending 的运行中更新或最终封存请求后，推进模拟时钟 10 分钟，下一轮不生成卡片、镜像快照冻结、没有失败日志和最终文字兜底；让请求转为拒绝后，下一轮恢复。同一 Session 的另一个同步目标也会被挂起的飞书封存拖住。

临时原型复用了 `waitForFileOperation()` 的现有等待实现，放在 SDK 创建和更新调用边界，保持原 Bridge 与 Host 协调器。4 个验证用例通过：创建挂起、运行中更新挂起、最终更新挂起均在模拟 15 秒后解除阻塞并完成下一轮；另一个同步目标能够收到最终答案。前三个用例还验证了迟到 SDK 成功不会恢复旧的本地控制流。

上述为方案阶段的原型结果，正式实现已补齐文字入口、取消、迟到拒绝及真实网络验证。本次保护限定已复现的飞书 SDK 等待；目标查询或状态写入自身永久挂起需要对应复现，不能据此宣称所有异步任务都具有期限保证。
