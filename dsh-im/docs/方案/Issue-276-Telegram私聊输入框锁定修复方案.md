# Issue #276：Telegram 私聊输入框锁定修复方案

日期：2026-09-28。分析基线：`75d07d6`，dsh-im `4.28.1`。

状态：代码已合并并推送到 main，自动化检查、本机 Telegram 实测及用户手机端确认已完成（2026-10-01）。第 1～8 节保留设计依据与验收要求，实际改动及验收结果见第 9～12 节。实测发现的模型失效时卡住问题另列为待修复项。

需求来源：[Issue #276](https://github.com/xmanrui/dsh-im/issues/276)。本方案以改动简单、复用已有机制、控制回归范围为原则。

## 1. 采用的方案

**Telegram 私聊在使用单条消息展示进度时，直接复用现有群聊的“创建占位消息 → 编辑进度 → 原位写入最终答案”流程。**

移除 `TelegramBotClient.openDeliveryStream()` 内按 `chatType === 'private'` 选择 Rich Draft 的分支，让私聊和群聊使用同一段现有代码。思考过程留痕仍优先使用原有 `openThinkingStream()`；只有进入 `openDeliveryStream()` 的回复使用占位消息，包括思考流打开失败后的回退。

这次不实现 `can_stop`、`stopped_message_generation`、活动草稿表或新的任务身份机制，也不增加预览方式设置。这些机制适用于必须保留原生 Draft 的产品选择；当前需求可以通过已有消息编辑能力解决，不必扩展任务控制链路。

方案取舍如下：

| 方案 | 能解决的问题 | 改动与取舍 |
| --- | --- | --- |
| 继续 Rich Draft，接入原生停止事件 | 用户可以点击按钮中断 | 需要事件订阅、草稿关联、停止协调及迟到事件处理；并不保证任务运行期间能直接发送 `/steer` |
| **复用占位消息编辑，本次采用** | 绕开 Draft 对发送入口的占用，让现有 `/stop`、`/steer` 和普通消息能够发出 | 主要修改 Telegram 的流选择；私聊展示方式变为普通消息原位更新 |

Telegram Bot API 支持通过 `editMessageText` 的 `rich_message` 参数编辑富文本，项目群聊路径已经使用该能力。最终答案无需降级为纯文本。[官方接口](https://core.telegram.org/bots/api#editmessagetext)

## 2. 修复后的用户行为

1. 用户发起任务，机器人发送一条“正在处理…”占位消息。
2. 有工具状态或文本进度时，更新同一条消息；没有新内容时保留现有消息，不发送保活草稿。
3. 用户可在生成期间发送消息。`/stop`、`/steer` 沿用现有控制命令处理，普通补充消息沿用现有会话队列。
4. 最终答案写回占位消息；长答案按现有拆分方式补发剩余部分，文件按现有附件流程发送。
5. 提问、审批和回答仍使用现有消息、按钮及处理机制。

“可以发出普通消息”不等于“自动插入正在执行的任务”。需要影响当前任务时仍使用 `/steer`。命令权限、任务尚未启动时的 `/stop` 行为，以及任务已完成时的提示，都保持现有语义。

可见变化需要写进发布说明：

- 原生 Draft 动画改为普通消息编辑；Android 和 Desktop 使用相同的服务端输出方式。
- 最终答案通常保留在最初占位消息的位置，期间用户发送的新消息可能排在它下面。
- 单条进度模式不再靠 Draft 心跳持续显示 typing；“正在处理…”或最近一次进度消息会一直保留。
- 进程异常退出时可能留下尚未完成的占位消息，这是复用现有群聊模式的生命周期特征；本次不增加跨重启清理服务。

## 3. 现有机制如何复用

| 现有代码 | 本次用途 |
| --- | --- |
| `telegram-runtime.mjs` 的 `openDeliveryStream()` 群聊分支 | 私聊也创建占位消息并编辑同一 message ID |
| `TelegramDeliveryStream` 的 `update()`、`#enqueue()` | 继续去重相同进度、串行发送，保证最终写入排在已有更新之后 |
| `#editRich()` | 最终富文本原位更新，拆分长答案，记录所有消息 ID |
| `#sendPlain()` | 富文本明确失败后的文本回退，以及错误提示替换占位消息 |
| 共享桥的 `isControlCommand()`、`#processFastCommand()` | `/stop`、`/steer` 绕过普通任务队列，沿用权限和任务归属检查 |
| `runControlCommand()`、`stopActiveTurn()` | 原样复用任务停止、补充指令和后台任务停止能力 |
| 共享桥的 `finish()`、失败与附件处理 | 保留部分答案、停止提示、文件投递和投递状态语义 |

无需新建停止回调、事件路由、Map、定时器或持久化记录。原生 Draft 不再由这条用户回复路径发出，也就不存在“旧草稿停止事件误停下一轮”的新增风险。

## 4. 具体修改

### 4.1 调整 Telegram 流选择

修改 `src/channels/telegram/telegram-runtime.mjs`：

- 删除 `openDeliveryStream()` 中创建私聊 Rich Draft 的条件分支。
- 原有占位消息代码直接成为私聊、群聊和话题共用的实现，不复制一份私聊版本。
- 移除仅该分支使用的 `randomInt` 导入。
- 添加简短注释，说明使用普通消息编辑是为了避免 Telegram Android Draft 占用发送入口。

保留原有参数传递：创建占位消息时带上 `chatId`、`replyToMessageId`、`messageThreadId`；之后使用返回的 `message_id` 编辑。最终多段答案继续使用现有话题路由。

`TelegramDeliveryStream` 的 `keepalive` 默认已经是 `false`。使用这个默认值即可，共享桥会自动跳过定时保活，不需要修改共享桥。也不能为了保持 typing 而把该流重新标记为短期草稿。

### 4.2 保持最终回复和错误回退

继续使用现有占位消息分支的三个回调：

- `update`：工具状态用普通文本编辑，答案进度用富文本编辑。
- `finish`：调用 `#editRich(target, messageId, block)`。
- `fail`：调用带 `placeholderMessageId` 的 `#sendPlain()`。

流创建失败时，共享桥已经可以继续执行并使用最终投递兜底；中间更新失败也已有日志和继续执行机制。不要增加失败后切回 Rich Draft 的路径，否则会重新引入输入框锁定。

保留既有投递结果结构和 `presentation` 值。本次不顺带重命名 `telegram-rich-draft` 等历史标识，不改变消息回执协议。

### 4.3 覆盖“最后一次预览等于最终答案”

改为编辑式输出后，最终答案可能与最后一次进度完全相同。这是本次复用需要重点补齐的正常场景：不能把 Telegram 明确的“消息内容未变化”响应当作投递失败，触发纯文本降级或重复发送。

先增加可复现的用例。若返回的是 `providerCode === 400` 且错误描述明确包含 `message is not modified`，在 `#editRich()` 的首段编辑和 `#sendPlain()` 的占位编辑处，将该次编辑视为目标内容已经存在，继续原有剩余分段发送和回执处理。判断用同文件内一个小函数复用，不改变 API 包装层对其他调用的错误语义。

严格区分其他 400 错误、429 限流、超时和网络结果不确定；这些继续进入现有失败或不确定结果分支。不能因为 `#lastUpdate` 相同就跳过最终发送：当前字段在请求成功前就被写入，不能证明内容已经送达。

相同内容错误可见于 [Telegram 官方仓库问题记录](https://github.com/tdlib/telegram-bot-api/issues/624)。实施时仍需用实际返回格式核对严格匹配条件。

### 4.4 限制修改范围

本次不修改以下业务代码：

- `TextHarnessBridge` 的任务队列、命令快通道、提问和审批处理。
- `HarnessClient` 的控制归属、停止、部分答案和附件处理。
- `askInWorkspaceSession()` 的绑定和重试流程。
- Telegram 更新订阅、消息解析、权限和配置存储。
- 思考过程留痕默认值、`openThinkingStream()`、其他 IM 渠道。

暂时保留 `sendRichMessageDraft()` API 包装和既有通用保活接口，不做无关删除。共享桥的保活测试继续保留，思考流也仍需要现有 typing 行为。历史 #175 修复及实测记录不改写。

## 6. 自动化验证

优先复用现有测试夹具、可控 Promise 和参数化测试，避免依赖长时间睡眠。

### 6.1 流与投递

1. 私聊创建一次占位消息；工具状态、文本进度和最终答案编辑同一消息；`sendRichMessageDraft()` 调用次数为零。
2. 群聊、超级群及私聊话题均保持正确的 chat、reply 和 thread 参数；现有群聊断言仍成立。
3. 相同进度去重；`keepalive === false`，手动 `refresh()` 不发送请求；长静默期间不创建新消息或草稿。
4. 人为挂起一次编辑，再发起 `finish()`，确认最终写入在后，完成后的迟到更新不覆盖答案。
5. 最终内容与最近进度相同：明确的未修改响应视为成功，不重复发答案，不丢富文本格式，长答案剩余分段仍发送。
6. 富文本明确拒绝时原位回退文本；消息无法编辑时沿用已有后备投递；超时或未知投递结果不盲目重发。
7. 长答案、代码块、Emoji、纯文件完成和多附件保留现有拆分及消息 ID 回执；处理中占位最终被答案、完成提示或错误替换。
8. 中英文占位与失败提示沿用现有语言设置。

原先要求“私聊必须创建 Draft”的测试要改成新行为的回归测试；API 包装层的 Draft 参数测试仍可保留。原先“在途刷新先于最终帧”的适配器测试改成“在途编辑先于最终帧”，保留它所保护的发送顺序。

### 6.2 控制命令与交互

1. 在 Harness 长任务等待期间，通过真实适配器链路接收 `/stop`，确认不等待普通任务队列，仍把既有控制归属传给 `stopActiveTurn()`。
2. 独立用例发送 `/steer`，确认任务继续运行且补充指令到达现有 `steerActiveTurn()`。
3. 普通追加消息可被接收，按原队列在前一任务后处理，不悄悄变成 steer 或并发新任务。
4. 提问按钮、自由文本回答、审批及拒绝仍能完成；有无留痕都不出现 Draft 调用。
5. 私聊权限拒绝仍有效；不同聊天和话题不串线；思考留痕模式继续输出独立过程消息。

已有用例能覆盖的权限、Harness 停止竞态和共享桥行为直接运行，不为了此修复另建控制命令体系。

### 6.3 检查顺序

先运行 Telegram 相关测试和已有共享桥、控制命令测试，再执行仓库现有的 `npm run check`。测试和真机结果应在实施后记录，不能把本方案中的验收项写成已经通过。

## 7. 真机验收

Android 是必测客户端；Desktop 用于回归，iOS 在可用时补测。自动化 API 替身不能证明手机输入框是否被占用。

1. 关闭思考留痕，运行持续至少 45 秒的任务，确认静默超过旧 Draft 存活窗口后，进度消息仍存在且输入框可发送。
2. 在独立任务中分别测试 `/stop`、`/steer` 和普通补充消息，核对停止、补充和排队语义。
3. 测试长回复、代码块及文件结果，确认最终内容完整、无重复答案，话题和引用正确。
4. 测试需要提问及审批的任务，确认按钮和输入回答可用。
5. 打开思考留痕，确认过程消息及最终回复保持原有行为；回归群聊和 Topics。
6. 检查连续文本更新是否出现明显限流、最终收尾是否成功。先复用现有最新进度模式和串行写入，不预先添加第二套节流、重试队列；若复现最终投递缺陷，记录具体失败并在 Telegram 层做最小修正后再验收。

本次不承诺取消已完成工具动作的外部副作用，也不改变现有任务取消时机；验收针对发送入口恢复及既有命令能力可达。
