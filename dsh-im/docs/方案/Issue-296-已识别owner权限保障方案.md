# Issue 296 已识别 owner 权限保障方案

本方案落实一条规则：已经确认身份的机器人 owner，默认可以发送消息和执行命令，不受普通用户白名单、默认命令权限和用户行设置限制。只处理能够通过现有接入流程或现有凭据确认 owner 的渠道，尽量复用已有代码。

结论：保留现有“owner 先放行，其他人再检查白名单”的机制，完善身份保存和回归验证，为 Discord 补充官方 owner 查询，并修正飞书的输入防错和排障提示。无需重建权限系统。

需求来源：[Issue 296](https://github.com/xmanrui/dsh-im/issues/296)。核查与实施日期：2026-10-01。核查基线为本地 4.34.0，并对照了 v4.32.0 的相关代码。方案已在 `codex/issue-296-owner-access` 分支实施，验证范围见文末实施记录。

## 范围与身份定义

本期的 owner 沿用产品现有含义：接入流程确认的扫码者、绑定账号本人，或者平台 API 返回的应用所有者。扫码接入者不一定是最初在平台后台创建应用的人；本期不追溯历史创建者。

| 渠道 | 身份来源 | 本期范围 |
| --- | --- | --- |
| 微信 | 扫码返回的 `ilink_user_id`，保存为 `ownerUserId` | 已支持的私聊场景；保留现有实现，补生产链路回归 |
| 飞书 | 扫码返回的 `user_info.open_id`，保存为 `ownerOpenIds` | 私聊和群聊；保证真实 owner 身份保留，修正文案和输入防错 |
| QQ | 扫码返回的 `userOpenid`，保存为 `ownerUserOpenid` | 确保私聊 owner 豁免；群聊保持现有精确 ID 匹配，不新增推测映射 |
| WhatsApp | 关联设备认证确认的 `accountJid` | 已支持的本人会话和群聊；复用现有 JID 匹配及消息防回环规则 |
| Discord | 使用已有 Bot Token 查询应用所有者 | 新增 owner 识别，接入现有私聊和群聊权限入口 |

QQ 的 SDK 将私聊 `user_openid` 和群聊 `member_openid` 分别作为发送者 ID。目前代码没有建立两者之间的身份映射，也没有足够证据确认它们在所有接入情况下相等。因此本期保证可确认的私聊身份；群聊只有发送者 ID 能命中已确认 owner 时才豁免。未确认的群聊身份按原策略处理，不以昵称、QQ 号或第一条消息推断 owner。

钉钉、企业微信机器人、企业微信应用、Telegram、Slack、iMessage、Matrix、邮箱先不增加 owner 识别。AI Office 使用原有设备和任务授权机制，不纳入这次 IM 白名单改动。钉钉现有 `approvedSenders` 特权机制保持原样，避免影响已批准用户。

飞书和 QQ 手动凭据接入后只有 `*` 的配置，也属于尚未确认 owner 的情况。本期不新增配对码、手动指定 owner、通讯录选择、OAuth 接入或身份映射系统。

## 已确认的现状

共享入口 `evaluateInboundAccess()` 已先调用 `accessPolicy.isPrivileged()`，命中后直接允许；只有未命中者才进入 `evaluateAccessPolicy()`。Host 的 `privilegedSenderIdsFor()` 已读取微信、飞书、QQ、WhatsApp 的真实身份字段。因此这四个渠道并非都缺少 owner 豁免。

飞书和 QQ 的 `*` 是旧的开放访问标记，不是某位用户的身份。代码有意将它排除在特权用户之外。把 `*` 改为“所有人都是 owner”会让白名单和命令限制失效，不采用该改法。

v4.32.0 与当前飞书扫码流程都会保存扫码者的真实 Open ID；手动凭据接入在没有历史 owner 时才使用 `['*']`。Issue 报告“扫码接入但只有 `['*']`”的配置来源尚未确认，不能据此声称已经定位到某条丢失 owner 的代码。实施时应通过接入方式和配置变更过程核对，不预先重写正常扫码逻辑。

现有拒绝路径会记录消息已处理；只有“可以聊天但不能执行命令”才回复权限提示。未在白名单中的用户被静默拒绝，这是原有设计。白名单输入也没有飞书机器人自身 ID 的语义校验。

现有部分渠道测试通过手工构造 `isPrivileged()` 证明 owner 可以放行，却没有同时验证“真实配置 → Host provider → 渠道入站”的连接。本期重点补上这段验证。

## 最终行为

| 情况 | 预期结果 |
| --- | --- |
| 已确认 owner，白名单为空或不包含本人 | 普通消息和已支持的本地命令可用 |
| 已确认 owner，被名单行设置为禁止命令 | 仍可执行命令，owner 身份优先 |
| 已确认 owner，开放模式默认禁止命令 | 仍可执行命令 |
| 普通用户在白名单且允许命令 | 保持现有行为 |
| 普通用户在白名单但禁止命令 | 可以聊天；命令返回现有拒绝提示 |
| 普通用户不在白名单 | 保持现有拒绝，不创建会话、不调用模型、不下载被拒消息的附件 |
| 没有已确认 owner，配置只有 `*` | 不产生任何 owner 豁免，按已保存的访问模式执行 |
| 机器人自己的 ID | 不自动获得人类 owner 身份 |

owner 豁免仅针对 dsh-im 的用户访问和命令权限检查。平台权限、群聊是否需要提及、消息类型支持、重复消息过滤、机器人防回环、会话路由及 Harness 工具审批继续按原规则执行。owner 身份不允许跳过工具执行审批。

## 微信 飞书 QQ 和 WhatsApp 的处理

这四个渠道优先保留业务代码。先补充测试，只有测试或真实复现证明某个配置写入路径丢失身份，才修复该路径。

接入和配置更新须维持以下约束：

1. 认证结果提供的真实 owner ID 通过现有配置存储持久化后，才创建使用它的运行实例。
2. 修改白名单、模型、工作区、别名以及普通重连，不清空或替换 owner。
3. 飞书重复扫码保留现有合并真实 owner 的规则，QQ 沿用现有扫码重新绑定语义，不新增 owner 转移机制。
4. 飞书已确认 owner 与 `*` 同时存在时，真实 owner 仍然豁免；`*` 本身始终没有特权。
5. 不在每条消息处理时调用平台查询身份，继续使用本机已确认配置。

`accessPolicyProvider()` 创建时会缓存特权 ID 集合，因此 owner 身份发生变化后，必须走现有接入或重连流程重建 provider。普通白名单保存只更新工作区策略，不需要重连；两者保持现有生命周期。

对仅剩 `*` 的旧飞书或 QQ 配置，不自动迁移为某个真人 owner，也不放宽白名单。用户可以在 DSH 中将本人加入普通白名单恢复使用；只有后续已验证的接入流程再次返回真实身份时，才能建立 owner 豁免。是否能通过现有扫码流程重新关联同一个机器人，需要按平台实际接入结果确认，不能承诺一次扫码必然修复旧机器人。

## Discord 的最小扩展

Discord 是本期唯一需要新增 owner 获取能力的渠道。官方应用对象提供 `owner`，团队应用提供 `team.owner_user_id`，当前应用查询可使用请求机器人的身份。[Discord 官方应用文档](https://docs.discord.com/developers/resources/application)

### 查询和身份选择

在 `DiscordApi` 增加 `getCurrentApplication()`，复用现有请求、鉴权、超时和错误处理，调用 `GET /applications/@me`。

个人应用采用合法的 `application.owner.id`；团队应用采用合法的 `application.team.owner_user_id`。团队应用不把所有成员都当成 owner，也不回退到服务器管理员或群主。返回的身份必须是有效用户 ID，且不能等于机器人自身 ID。

同一次查询必须确认 Token 对应的机器人与当前 `platformId` 一致：优先核对应用返回的 bot ID，缺失时复用 `getCurrentUser()`。不能把其他机器人身份查询得到的 owner 写进当前配置。

### 存储和接入位置

在 `DiscordConfigStore` 使用现成的 `normalizeBotExtension` 增加 `ownerUserId`，旧文件缺失该字段时按 `null` 读取，文件版本不变。`privilegedSenderIdsFor('discord', config)` 读取此字段。

在 `DiscordController` 包装传给父类的 `createRuntime` 回调：读取已保存配置，完成一次 owner 查询，将有效变更写回同一个 Discord 配置，再把最终配置传给原回调。原 production 回调会用它创建 `accessPolicyProvider()`，无需修改共享 controller 的生命周期或 Discord 消息 bridge。

这一位置同时覆盖首次绑定、启动已有机器人和现有重连。操作处于已有机器人串行生命周期内，不额外创建后台任务或周期轮询。整次 owner 查询使用 5 秒超时预算，限流时不重试，失败后继续创建运行实例。

需处理一个现有保存细节：共享 `bindCredentials()` 会重新组装基础配置，不带 Discord 扩展字段。为避免更新同一机器人 Token 时抹掉 owner，在 Discord 存储的局部保存适配中，只有调用方未提供 `ownerUserId` 时才继承同一 bot 的旧值；显式 `null` 表示清除。不要为此把所有渠道的配置更新都改成无条件合并。

### 查询失败和旧配置

| 情况 | 行为 |
| --- | --- |
| 首次查询成功 | 保存 owner 后创建 provider |
| 旧 Discord 配置没有 owner，启动时查询成功 | 自动补齐该字段，保留原白名单和所有工作区配置 |
| 超时、网络错误或限流 | 不授予新的身份；沿用已保存 owner，记录简短警告，继续原连接流程 |
| 没有历史 owner 且查询失败 | 继续按原访问策略运行，owner 暂未识别，不将连接判为失败 |
| 平台完整有效响应表明 owner 已变化 | 用新的已确认 owner 替换旧值，不累加历史所有者 |
| 返回结构不完整或身份不匹配 | 不据此更新配置，记录查询异常，不猜测 owner |
| owner 配置持久化失败 | 不把尚未成功保存的新身份用于特权放行；保留上次已提交配置并记录警告 |

owner 元数据失败不应中断本来正常的消息连接。缓存跟随机器人配置持久化；平台所有权转移在下一次成功启动或重连查询并保存后生效，本期不实现实时所有权变更订阅。

## 飞书设置防错与排障

### 页面说明

复用现有访问设置页，针对本期渠道将说明改为条件明确的文字：

> 已由接入流程确认的所有者可以访问并执行命令，不受本页限制。未识别到所有者身份时，按本页访问设置执行。

飞书增加一句短说明：

> 白名单请填写使用者的 Open ID，不是机器人的 Open ID。仅保存通配符的接入配置不包含所有者身份。

QQ 群聊说明注明：扫码获得的是私聊身份，群聊只有匹配已确认 owner 身份时才豁免。本期不新增用于展示完整 owner ID 的状态字段或接口。

未纳入本期的渠道不改变访问逻辑和专有设置流程。新增文案走现有国际化机制，补齐对应语言资源。

### 机器人自身 ID 校验

飞书保存名单时，将用户 ID 与当前机器人的真实 `botOpenId` 比较，匹配则提示“这里需要填写用户的 Open ID，不能填写机器人自己的 Open ID”。单纯检查 `ou_` 前缀不能区分机器人和用户，不作为解决办法。

Host 为最终校验方，使用该 bot 的实际配置；不要求把完整 `botOpenId` 新增到公开状态中。如果前端已有可靠的完整 ID，可提前提示；只有脱敏值时由保存返回的错误显示在现有 feedback 区域，不拿脱敏值做比较。

可在 `createWorkspaceAwareController()` 增加一个默认不处理的可选 `validateAccessPolicyForBot(botId, policy)` 回调，仅飞书 production 注入。回调在已有更新串行区间、原子写入之前读取当前 bot 配置并校验；其他渠道未注入时路径不变。既有 incarnation 校验、响应预构造及写入失败回滚继续保留。

校验针对提交后处于 `allowlist` 模式的场景。切换为 `open` 时允许保留隐藏名单里的历史错误条目，以免阻断恢复访问；再次启用这份名单时要求修正。不自动删除用户数据，不在启动读取旧配置时拒绝启动，也不禁止有意保存空白名单。

### 拒绝原因

飞书沿用拒绝陌生人时不回复的行为，在现有拒绝处理处增加一条可检索日志：渠道、botId、私聊或群聊、`sender-not-allowed` 等原因。使用现有 logger 和消息去重，不建立审计表、计数器或新的通知系统，也不输出完整用户 ID、消息正文和凭据。

保留“允许聊天但无命令权限”的现有回复。此次不向所有被拒用户自动发送新消息，以保持普通访问控制的现有行为。这样解决 Issue 的排障可见性诉求，不扩张消息发送流程。

## 兼容性要求

1. `workspaces.json` 的访问策略结构和 `bot.access-policy.set` 请求格式不变；已有策略不因补齐 owner 而重新初始化。
2. 微信、飞书、QQ、WhatsApp 沿用原有身份字段；Discord 只增加一个可选字段。
3. 不以 UI 提交值、消息正文、用户名、首个聊天用户、群主或机器人 ID 作为可信 owner 来源。
4. 不改变普通用户的开放模式、白名单和命令权限结果；钉钉已有批准用户的行为保持不变。
5. 不增加每条消息的网络请求。Discord 仅在现有运行实例创建流程查询，失败不阻断消息连接。
6. 白名单保存仍作用于后续入站事件；不取消已经开始的回合，不重建会话、不修改投递路由。
7. 保留群聊提及、Topic Session、语音转写后的命令复检、卡片操作和工具审批原有判断顺序。
8. 单个 bot 的 owner 不能影响同渠道其他 bot；删除后重建不能从已删除配置恢复旧身份。

这些约束由下述自动化回归覆盖；真实平台环境的验证边界单独记录，不以模拟测试代替平台实测。
