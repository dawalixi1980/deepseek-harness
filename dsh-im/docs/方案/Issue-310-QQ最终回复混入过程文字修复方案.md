# Issue 310 QQ 最终回复混入过程文字修复方案

方案日期：2026-10-04。实施更新：2026-10-05。状态：已实施，自动化检查与修复后的 winBot 实测均通过。

建议以工具调用作为过程与答复的分界：QQ 正常完成时只发送最后一次工具调用之后的助手正文，同一答复的文本分段继续合并。复用现有文本累积器，在正常回复和超时补发两处应用同一规则。采用一个内部布尔参数，只由 QQ 开启，其他渠道保持现有行为。

## 已确认的现象

[Issue 310](https://github.com/xmanrui/dsh-im/issues/310) 报告在 DSH 桌面版连接 QQ 官方机器人、使用 MiMo 时，过程文字出现在最终回复中。截图中“去查资料”“查回来了”等文字在桌面端属于折叠的执行过程，在 QQ 中与正文合并。

本机已通过 QQ 客户端向 winBot 发送真实私聊，环境为 DSH Desktop 0.2.0-rc.2、dsh-im 4.35.0。测试明确要求先发送带标记的过程说明，调用一次只读 `printf`，然后只给带另一标记的最终答案。

| 模型 | 会话记录 | QQ 实际结果 |
| --- | --- | --- |
| GPT-6.1 Sol，xhigh | seq 18 是过程文本及工具调用；seq 23 的正文只有最终答案 | 过程文本与最终答案合并 |
| DeepSeek Flash，high | seq 37 是过程文本及工具调用；seq 43 的正文只有最终答案 | 过程文本与最终答案合并 |

两轮工具均成功，回合均为 `completed`。测试后已恢复 winBot 原会话。原始证据保留在本机测试证据目录 `issue310-20261004/`，包括两张 QQ 截图、`events.json` 和 `summary.json`。

本机没有配置 MiMo。两次实测的 `reasoning` 文本均为空，因此实测证明的是普通过程文本被汇总到正文，不能据此认定 MiMo 的非空推理内容泄露，也不能把这两次测试当成非空推理过滤的实测。

## 原因

1. [`textFromHarnessContent`](../../src/channels/shared/harness-client.mjs) 只取 `type: text`，已经排除了标准 `reasoning` 块。但“我去查资料”这类面向用户的过程说明本身就是 `text`，仍会被保留。
2. 同一文件中的 `AssistantTextAccumulator` 按 `step/index` 累积文本。`setCanonical()` 只替换对应步骤；`text` 再把所有步骤用空行拼接。它没有在工具调用时区分过程和最终答复。
3. [`QqHarnessBridge`](../../src/channels/qq/qq-bridge.mjs) 的 `onUpdate` 只提取工具错误；正常完成后直接把 `ask()` 返回的累计 `answer` 交给 Markdown 发送函数。
4. [`extractCompletedTurnAnswer`](../../src/channels/shared/deferred-delivery.mjs) 在超时补发时也使用同一个累积器，存在相同问题。只修改 QQ 正常发送前的一行，会遗漏补发路径。

因此，即使模型的最后一条答复没有重复过程说明，插件仍会自行拼成“过程说明＋最终答案”。QQ 展示的是插件已经汇总好的字符串。

`progressMode: all` 决定进度回调交付哪些事件，不决定 `answer` 怎样汇总。改成 `latest` 无法修复本问题，还可能丢掉需要提示的工具错误。现有 tracker 测试明确要求跨步骤合并，故此前测试通过与此问题并不矛盾。

## 最小修改方案

增加一个内部参数 `finalAnswerOnly: true`，由 QQ 的 `askOptions` 和补发协调器固定传入。默认值为 `false`，不增加用户设置、配置存储或迁移。

继续保留现有的完整累计文本，供已有进度展示和停止后的部分回复使用。开启该参数时，额外复用一个 `AssistantTextAccumulator` 保存可作为最终答复的文本。它只处理本次请求已经确认归属的事件，不保存整份事件历史。

两条路径共用一个小的文本处理函数，放在现有共享模块内即可：

- 普通 `text-delta` 按现有的步骤和内容索引累积；完整 `assistant/message` 用其 `text` 块替换对应步骤。
- 遇到 `tool/call`，清空最终答复缓冲区，之前的文字归入过程。
- 完整助手消息本身含 `tool-call` 时，同样清空并跳过该消息的过程文本。这样不依赖完整消息与独立工具事件的先后顺序。
- 最新完整助手消息明确没有正文时，清空候选正文，不向前寻找较早的过程说明。这里只处理明确的空定稿，不把普通工具状态、推理片段当成空答复。
- 对只提供增量的记录，保留最后一次工具调用之后的增量拼接；遇到完整定稿时仍以定稿为准。没有步骤编号的旧格式继续按事件顺序处理，完整消息覆盖此前候选文本。

正常 `completed` 时取最终答复缓冲区。为空就走现有的“本轮处理已结束，没有文本回复”或附件完成分支，不回退到整轮累计文本。错误继续走既有错误处理；用户停止后保留既有部分回复行为，不把停止伪装成正常完成。

补发仍由现有协调器读取目标回合、确认终态和保证投递，不新增轮询或重试机制。仅将参数传给 `extractCompletedTurnAnswer`，使它用同一文本规则提取结果。参数属于每个 QQ 协调器的固定行为，进程重启后自然生效，无需写入待补发记录。

这比直接选择“最后一条非空消息”多保留了一个必要边界：同一最终答复可能有多个文本块或分段，不能误删；只有工具调用能明确证明前面的文本属于尚未完成的执行过程。无工具的普通问答保持原有文本合并方式。

## 修改范围

| 文件 | 修改内容 |
| --- | --- |
| `src/channels/shared/harness-client.mjs` | 为现有累积器提供清空操作及小型事件处理函数；开启参数时维护最终正文，正常完成时选择返回值 |
| `src/channels/shared/deferred-delivery.mjs` | 接收相同参数，复用最终正文提取规则 |
| `src/channels/shared/deferred-delivery-coordinator.mjs` | 接收并向提取函数透传参数 |
| `src/channels/qq/qq-bridge.mjs` | 正常请求和补发协调器都开启参数；现有工具错误提示、Markdown 和附件投递继续复用 |
| 相关现有测试文件与构建产物 | 加入行为回归，用正常构建生成 `lib/` |

不新增类、事件总线、持久化字段、后台任务或依赖。无需修改模型适配器，也无需按“我去查资料”等词语或正则删除正文。若模型把推理和答案混在同一个普通文本块中，这个结构化修复无法可靠区分，应另取该模型的原始事件确认。

## 验收

| 场景 | 预期 |
| --- | --- |
| 过程文本、一次或多次工具调用、最终正文 | QQ 私聊和群聊最终只包含最后一次工具调用后的正文 |
| 最终正文含多个块、多个增量或连续文本步骤 | 正文完整且顺序正确；完整定稿替换草稿，不重复 |
| 非空 `reasoning` 与正文共存 | 最终正文不包含推理测试标记；用确定的事件夹具验证 |
| 过程文本后仅执行工具，或最后定稿为空 | 不回退发送过程文字；使用原有无文本或附件完成处理 |
| 超时后完成，含进程重启后的补发 | 使用相同提取规则，只补发最终正文 |
| 错误、停止、文件返回、工具失败提示 | 保持既有终态及投递行为 |
| 未开启内部参数的其他渠道 | 原跨步骤累积和进度回调保持不变 |

先给现有 tracker、QQ bridge 和补发测试加入回归，包含工具事件与完整消息的顺序变化、缺少步骤编号的记录。再运行相关测试，最后执行一次 `npm run check`。完整检查通过后，在 winBot 重发本次两条测试消息，核对 QQ 只出现 `FINAL` 行，并用会话记录确认 `PROGRESS` 行仍正常存在于执行过程。测试完成后恢复原会话。
