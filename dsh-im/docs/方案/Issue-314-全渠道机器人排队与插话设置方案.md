# Issue #314：全渠道机器人排队与插话设置方案

日期：2026-10-07（Asia/Taipei）。状态：已实现，自动化检查与本机飞书验收通过，待随下一个版本发布。

关联：[Issue #314](https://github.com/xmanrui/dsh-im/issues/314)、[Issue #115](https://github.com/xmanrui/dsh-im/issues/115)。

## 目标与原则

按“每个机器人一个设置，复用现有排队和 `/steer` 机制”实现全渠道的普通消息排队／插话选择。

Issue 的后续反馈希望通过设置省去每次输入 `/steer`，并指出排队缺少提示、长任务容易被误认为卡住。根据本次讨论，功能收敛为：

- 设置按每个已接入的机器人／账号实例独立保存。
- 入口为“机器人 → 更多设置 → 通用”。
- 只有“排队”和“插话”两种模式，默认排队。
- 不提供“跟随 DSH”，不读取或同步 DSH 输入框的发送模式。
- 尽量复用现有配置存储、管理接口、队列、权限、消息去重和 `/steer` 执行链。
- 不引入新的任务调度系统，不重构所有渠道的 Bridge。

## 1. 设置入口和作用范围

当前“更多设置”的公共页签包含投递、访问设置。新增公共的“通用”页签，所有聊天渠道复用同一个页面组件。

设置名称：**任务运行时的新消息处理方式**。

| 选项 | 说明 |
| --- | --- |
| 排队（默认） | 当前任务结束后，再处理新消息。可使用 `/steer` 手动插话。 |
| 插话 | 将新的纯文字消息作为补充指令加入当前任务，Agent 在下一步读取。 |

页面补充说明：

> 没有正在运行的任务时，正常开始新任务。图片、文件、语音和带引用的消息按原有方式处理。

设置的作用范围和生效规则：

- 同一机器人的私聊、群聊、Topic、Thread 都使用该设置，各聊天之间仍保持现有隔离。
- 不同机器人分别保存，互不影响。
- 新机器人和旧配置缺少该字段时，都使用“排队”。
- 保存后对新收到的消息生效，不要求重启。
- 已经排队或已经提交插话的消息不重新处理。
- 没有全局默认继承、会话级覆盖或批量同步设置功能。

## 2. 消息处理规则

自动插话只改变普通纯文字消息的处理方式，其他已有交互优先级保持不变。

| 收到消息时的情况 | 处理方式 |
| --- | --- |
| 设置为排队 | 完全沿用现有处理流程 |
| 设置为插话，当前聊天有可控制的运行任务 | 提交补充指令，不进入普通消息队列 |
| 设置为插话，但没有运行任务或任务尚未启动 | 沿用普通流程，正常执行或排队 |
| 显式发送 `/steer 内容` | 沿用现有命令行为，与设置无关 |
| 正在回答问题、审批、选择菜单或收集批量输入 | 优先按原交互处理 |
| 图片、文件、语音、带引用的消息 | 完整保留原消息，走原有流程，不截取文字单独插话 |
| 当前任务属于另一个聊天 | 不插话，沿用现有会话归属限制 |

已识别的命令继续执行原命令。未知的斜杠文本仍按现有规则视为普通输入，不新增一套命令识别规则。

群聊继续遵守现有提及规则、白名单和命令权限。自动插话要求发送者具备原 `/steer` 的执行权限；只有普通聊天权限的人，其消息继续排队，不因为开启此设置获得控制权限。

无需增加新的权限选项，也不新增“只能由任务发起人插话”的限制。仍以现有聊天和活动回合的归属检查为准，不接管其他聊天或外部入口发起的任务。

## 3. 配置、页面和接口

只增加一个枚举字段：

```text
busyMessageMode: "queue" | "steer"
默认值："queue"
```

复用 `src/channels/shared/bot-workspace-store.mjs` 中的 `BotWorkspaceStore`，按 `botId` 保存，沿用已有的持久化、机器人删除清理和状态返回机制，不另建配置文件或数据库。

具体改动：

1. 状态响应增加 `busyMessageMode`。
2. 增加一个保存接口，例如 `bot.message-mode.set`，只接受 `botId` 和上述枚举值。
3. 沿用现有管理接口的权限验证和保存错误处理。
4. Runtime 通过配置读取函数获取当前值，仿照已有上下文增强配置的接入方式。
5. 每条消息接收时确定模式，后续不会因为用户修改设置而改变这条消息的处理方式。
6. 页面复用现有表单、保存按钮、反馈样式和国际化机制。

保存失败时，页面给出失败反馈，运行中的配置继续保持原值；重启后从既有存储恢复。缺少字段按 `queue` 读取，不要求用户迁移旧配置。

公共页签接入点为 `plugin-src/client/delivery-settings.js` 中的公共页签定义及页面分支。新增通用页即可，不重构整个设置页面。

## 4. 核心实现：入队前增加一次分流

在各渠道处理完命令、审批、问题回答等已有分支后，普通消息进入原队列之前，增加自动插话判断。

```text
现有去重、访问权限和会话识别
→ 现有命令、菜单、审批、问题回答、批量输入
→ 判断是否满足自动插话条件
    → 满足：尝试提交到当前运行任务
    → 不满足：进入原有消息处理流程
```

复用 `src/channels/shared/control-command.mjs` 中已有的会话解析、来源增强和 `steerActiveTurn()` 调用。可将其中提交补充指令的少量逻辑抽成共享函数，让手动 `/steer` 和自动插话共同调用。

该函数只需要区分以下结果，不设计复杂状态机，也不通过匹配中文回执判断是否成功：

| 结果 | 后续动作 |
| --- | --- |
| 成功提交 | 结束本条消息的输入处理，等待原任务统一回复 |
| 明确未提交，例如任务已结束 | 将完整消息交回原有流程 |
| 抛出错误，例如网络超时 | 沿用现有错误处理，不自动再次入队 |

网络超时可能意味着已经提交成功，不能再作为普通消息执行一次。

必须保持的约束：

- 使用现有活动回合归属检查，不用“队列非空”代替“任务正在运行”。
- 插话成功后，即使回执发送失败，也不能重新提交任务。
- 沿用消息 ID 去重、来源记录和会话同步去重。
- 同一聊天连续收到多条消息时，按接收顺序完成分流和插话提交。复用现有 Promise 串行写法，只等待提交动作，不等待整轮任务结束。
- 不将自动插话挂在等待整轮任务结束的普通队列后面。
- 不为了等待第一轮启动而新增定时重试、轮询或消息合并机制。
- 不改变 `/stop` 和显式 `/steer` 的已有含义，不扩大现有 `/steer` 可控制的任务范围。

关键复用位置：

| 现有代码 | 复用内容 |
| --- | --- |
| `src/channels/shared/control-command.mjs` | 会话解析、补充指令来源增强、手动 steer 行为 |
| `src/channels/shared/harness-client.mjs` | `steerActiveTurn()`、活动回合归属校验、输入来源登记 |
| `src/channels/shared/workspace-session.mjs` | 当前工作区和会话的现有访问方式 |
| `plugin-src/host/harness-session-coordinator.mjs` | 当前 Host 中已有的活动回合校验和指令注入 |
| 各渠道现有 `accept()`、快速命令与入队方法 | 消息去重、交互优先级、回执、普通任务队列 |

## 5. 全渠道接入

共享逻辑接入现有 13 个聊天渠道：

| 接入方式 | 渠道 |
| --- | --- |
| 修改共享 `TextHarnessBridge`，各渠道传入配置 | Telegram、Slack、Discord、WhatsApp、iMessage、邮箱、Matrix |
| 在各自 Bridge 的入队前调用同一共享函数 | 飞书、微信、企微机器人、企微应用、钉钉、QQ |

共享消息处理层为 `src/channels/shared/text-harness-bridge.mjs`。独立 Bridge 只增加接入代码，不复制整套策略。

各渠道继续负责自己的消息解析、回执发送、提及和线程识别。共享函数只负责尝试插话，不再抽象一个覆盖所有渠道的新 Bridge。

AI Office 边界：当前 AI Office 是任务连接器，没有普通聊天消息的追加入口，所以该设置对其现有协议不适用，不显示一个无法生效的开关。为它新增追加指令协议需要 Office 服务端配合，不混入本次聊天渠道改动。

## 6. 用户反馈与范围控制

为解决 Issue 中“不知道消息有没有被接收”的问题，只增加必要的文字反馈，复用现有发送接口：

| 实际结果 | 回执 |
| --- | --- |
| 插话成功 | 已提交补充指令，Agent 会在下一步读取。 |
| 消息确实需要排队 | 已排队，等待前序消息处理。 |

回执只说明实际处理结果。立即开始执行的普通消息不发送“已排队”；没有成功提交插话时，不发送“已提交补充指令”。

不增加队列编号、进度卡片或新的回执开关。发送失败走现有日志与错误处理，不影响已经确定的消息去向。

本次不包含：

- 跟随 DSH 输入框设置。
- 全局继承、会话级模式、批量复制机器人设置。
- 队列查看、撤回、编辑、重新排序或排队消息转插话。
- 执行进度展示、思考过程展示。
- 图片、文件、语音或引用消息的 steer 能力扩展。
- 自动理解消息意图，以此判断它是新任务还是纠正指令。
- 新任务调度器、持久化消息队列或全渠道 Bridge 重构。
- AI Office 追加指令协议扩展。

### 消息分流与竞态

- 排队模式保持原行为。

- 空闲时正常提交；任务尚未启动时沿用原流程。
- 任务结束竞态中，明确未提交的消息进入原流程，最终只处理一次。
- 连续消息的分流和插话提交顺序正确。
- 重复投递不重复执行，提交超时不盲目重发。
- 插话已经提交、但回执失败时，不重新入队。

### 原有功能与隔离

- 手动 `/steer`、`/stop`、其他命令、审批、问题回答、菜单和批量输入保持原行为。
- 附件和引用完整保留，语音沿用原流程。

## 9. 实现与验收记录

### 最终实现

- `message-mode.mjs` 集中定义两种模式和保存参数校验。`BotWorkspaceStore` 在现有配置中按机器人保存 `busyMessageModes`，只存非默认值，保存成功后才更新运行值；删除机器人同步清理。
- 公共 `BotGeneralSettingsPage` 放在“更多设置 → 通用”，复用现有管理 RPC 和表单样式。全部 13 个聊天渠道接入 `bot.message-mode.set`；读取失败时禁用保存，保存失败可重试，切换机器人不会混入旧请求结果。
- `BusyMessageDispatcher` 仅串行处理同一聊天的分流和提交，原有任务队列保持不变；手动与自动插话共用从 `control-command.mjs` 提取的 `steerMessage()`。
- 共享 Bridge 与六个独立 Bridge 接入同一分流逻辑。Discord 在线程路由前、钉钉在异步回调前固定收到消息时的模式，其余入口在同步接收路径固定模式。
- 已补齐中文、英文说明与必要回执。未增加依赖，也未更改版本号或发布 npm 包。
